## What this is

Lykompanion — a local, voice-first gaming companion. FastAPI backend + vanilla HTML/CSS/JS frontend (no build step, no framework, no bundler). All LLM calls go through OpenRouter (optionally Google AI Studio or any OpenAI-compatible endpoint). Windows-only for several features (OCR, Windows Graphics Capture, per-app volume). The [README.md](README.md) is thorough and kept current — consult it for feature behavior, config variables, the API endpoint table, and the agent tool table before reading code.

- `RUN.cmd` / `run_app.py` = native desktop app (pywebview/EdgeWebView2 wrapping the same server, plus a per-launch API token `LYKO_API_TOKEN` that the middleware in `app/main.py` enforces on `/api/*`). Dev uvicorn runs with no auth. The window is **frameless** (`frameless=True, easy_drag=False`): the web UI draws its own titlebar (`.titlebar` in `web/index.html`, styled in `style.css`, gated by `body.desktop-app` which `web/js/app/init.js` adds only when `window.pywebview` exists). Minimize **hides to a `pystray` tray icon** (Open Lykompanion / Quit; double-click = open); close and tray-Quit both go through `_quit()` in `run_app.py` (stops the tray loop + `win.destroy()`). Window controls are Python functions exposed via `win.expose(...)` (`window_minimize`/`window_close`/`window_set_bounds`/`window_save_bounds`, alongside `download_voice`), called from `init.js` as `window.pywebview.api.*`. **The titlebar drag, resize, maximize AND Windows-style snap are all driven from JS through pywebview's own `win.move`/`win.resize`** (the single exposed `window_set_bounds(x,y,w,h)`), NOT by mutating the window style: an earlier attempt to add `WS_THICKFRAME` on the WinForms HWND via ctypes for OS-native resize/snap **broke the window-drag entirely** — do not reintroduce it. `init.js` **owns the titlebar drag itself** (there is deliberately NO `pywebview-drag-region` class — pywebview's native drag can't report mouse position mid-drag, which snap needs): `pointerdown` on `.titlebar-drag` moves via `window_set_bounds` per rAF, and dragging into a screen edge snaps on release (top=maximize, left/right=half, computed from `screen.avail*`, with a `restoreBounds` to un-snap to). Frameless windows have no OS resize border, so there are also 8 thin `.resize-grip` edge/corner strips (desktop-only) doing the same delta math. Double-click `.titlebar-drag` = maximize when floating; when already maximized it shrinks to a **half-size window centered on the work area** (not a restore to the previous rect). This is a pure-JS snap reimplementation — **no OS snap overlay/layouts, no Win+Arrow** (the OS eats the Win key before JS sees it). Uses logical px throughout; `setBounds` scales by `devicePixelRatio` for pywebview (physical px) while `window_save_bounds` persists logical px. **Window position+size persist across restarts**: every gesture end calls `window_save_bounds` → `_save_window_state` writes `data/window_state.json` (logical px); `main()` reads it via `_load_window_state` and passes `x/y/width/height` to `create_window` (falls back to centered 1280×820; rejects sub-min sizes). `_clamp_window_state` recenters on the virtual desktop if the saved titlebar center is off every connected monitor (physical `GetSystemMetrics` ÷ `GetDpiForSystem` scale to compare against logical bounds). The Win11 DWM window-border outline is removed in the `loaded` handler via `_remove_window_border` (`DwmSetWindowAttribute` `DWMWA_BORDER_COLOR=DWMWA_COLOR_NONE`) — this is a DWM *attribute*, not a window style, so it's safe (unlike the reverted `WS_THICKFRAME`).

## Architecture

Request path: `web/js/app/chat-stream.js` → `/api/chat/stream` (SSE, primary) or `/api/chat/voice[/stream]` (raw audio sent directly to an audio-capable model — no local STT unless `transcription_enabled`) → agentic tool loop → streamed reply narrated sentence-by-sentence via TTS.

### Agentic tool loop — `app/api/chat.py`
The heart of the app. `_run_chat_with_tools` (non-streaming) and `_stream_chat_with_tools` (SSE) re-call the model while it requests tools, up to `MAX_TOOL_ITERATIONS = 8`. All tool specs are concatenated into `ALL_TOOLS` at the top of the file and passed on every call — the model self-selects.

**To add a tool**: create `app/services/llm/<name>_tool.py` exporting a `*_TOOLS` spec list (OpenAI function format) and an `execute_*` function; add both to `ALL_TOOLS` and the dispatch in `_execute_tool_impl` in `app/api/chat.py`; document it in the README tool table. Memory tools are the exception — they live together in `app/services/llm/tools.py`.

Tools with frontend-visible side effects (volume change, stop_listening) are emitted as out-of-band SSE events (`volume`, `stop_listening`) interleaved with `delta` text events; non-streaming responses carry them as extra JSON fields.

### Layering
- `app/api/*` — route handlers, one module per concern. Registered in `app/main.py` (which also holds the token middleware, the SSRF-hardened `/api/proxy/image`, and the `lifespan` that starts two background pollers: game-state OCR and reminders).
- `app/core/*` — settings + persistence stores. Each store is a small module owning one JSON file in `data/` (memory.json, chats.json, usage.json, game_state_sessions.json, game_state_trackers.json, reminders.json, ...). Flat-file JSON everywhere; no database.
- `app/services/llm/*` — OpenRouter/OpenAI-compatible client (`client.py`, also handles provider selection + usage/debug recording), one module per agent tool, and the two background LLM passes: `memory_extraction.py` (fire-and-forget after every exchange) and `game_state_extraction.py` (the OCR poller).
- `app/services/tts|screenshot|ocr|system` — provider backends. Two screenshot paths exist deliberately: `capture.py` (mss/GDI, on-demand vision) vs `wgc_capture.py` (Windows Graphics Capture, used by the high-frequency OCR poller because GDI causes in-game stutter).
- **Native overlay** (`overlay/` at repo root, NOT Python): a standalone C++ exe (`overlay/overlay.cpp`, single TU, `build.cmd` → `Lykompanion-overlay.exe`) drawing a game-state panel + reply/reminder toasts over the game via layered windows + Direct2D (no GDI paint, no injection). It hosts its OWN named-pipe API (`\\.\pipe\lykompanion-overlay`, newline-delimited JSON: `toast`/`image`/`memory`/`handsfree`/`game_state`/`edit_mode`/`quit`; `image` downloads a web URL via WIC and renders it as a toast; `memory` shows a brain +/- save/remove toast; `handsfree` toggles a persistent bottom-center live-mic indicator with a pulsing gradient; a `toast` may carry `duration_ms` to override the default lifetime); all rendering, input, edit mode (default hotkey Ctrl+Shift+O, now user-configurable — see below), and layout/appearance persistence (`%LOCALAPPDATA%\Lykompanion\overlay_layout.json`) live in the exe. Memory toasts render in their OWN draggable area (`g_memWin`, `g_memToasts`, bottom-right default), separate from the reply/reminder/image toasts (`g_toastWin`, `g_toasts`, top-right); both go through the shared `RenderToastList(list, win, anchor, ...)`. The edit-mode toolbar (`RenderConfig`/`ConfigClick`) exposes opacity, **text size** + **font** (`g_fontScale`/`g_fontIdx` → `RebuildTextFormats()` recreates the 5 scalable `IDWriteTextFormat`s; chrome formats `g_fmtUi`/`g_fmtCenter`/`g_fmtIcon` stay fixed), the accent picker, and per-area **show/hide** toggles (`g_showToasts`/`g_showMemories`/`g_showPanel`/`g_showHandsfree`). All of these persist in the layout JSON. Python (`app/services/overlay_process.py`) is ONLY a thin client: spawns it on `game_state.start_tracking` with `--parent <pid>` (overlay self-exits if we die), quits it on stop/app-exit, and pushes toasts (reply sentences streamed as they complete, reminders — but when narration is ON the frontend sets `client_overlay_toasts` on the chat request so the backend SKIPS reply toasts and `web/js/app/narration.js` pushes each sentence itself via `POST /api/overlay/toast` with `duration_ms` = its spoken length at the current TTS speed, so a toast stays up exactly while it's narrated instead of on a fixed timer), web images extracted from reply markdown (`_extract_overlay_images`, proxy-URLs unwrapped to the real source), + the game-state panel. `OVERLAY_ENABLED` gates it. Full plan/history in `TODO.md`; render approach + pipe protocol in `overlay/README.md`. This is the working native replacement for the reverted WebView2 overlay (gotcha below).
- **Overlay editor (hotkey/presets/gamepad)**: edit mode's hotkey is no longer hardcoded — `g_hotkeyMods`/`g_hotkeyKey` (loaded/saved in `overlay_layout.json`, changed live via a new `set_hotkey` pipe command or a fresh launch) back `RegisterEditHotkey`/`ReregisterEditHotkey`; the Settings UI (`web/js/app/settings.js`'s "Change…" button) captures a combo via a one-shot `keydown` listener, and `app/api/config.py`'s PUT handler both pushes it live (`overlay_process.set_hotkey`) and writes it into the layout file (`overlay_process.write_hotkey_to_layout_file`) so a not-yet-running overlay also picks it up (`RegisterHotKey` runs synchronously at startup, before the pipe is guaranteed to be listening). Layout persistence moved from "save on every drag/click" to a `LayoutPreset` array (`g_presets`/`g_activePreset`, one-time migration from the old flat JSON shape) with a real dirty/discard flow: `g_editSnapshot` is captured on entering edit mode, `g_dirty` tracks live changes, and the toolbar's Save/Discard & Close buttons plus a hotkey-triggered "Save & Exit / Discard & Exit / Keep Editing" confirmation prompt (`g_showExitConfirm`, only shown if `g_dirty`) replace the old unconditional save-on-exit. Presets get their own toolbar row (switch/new/delete + a mouse-only, keyboard-typed in-place rename via `GetAsyncKeyState`/`ToUnicode` polling — the layered windows never take keyboard focus, so no `WM_CHAR`). Full XInput gamepad support (`PollGamepad`, a `TIMER_GAMEPAD` timer running only while editing) mirrors every mouse action: D-pad/left-stick cycles a `g_selectedWidgetIdx` through `g_widgets[4]`, right-stick moves it directly, A/B/X/Y/LB/RB map to Save/Discard/Delete-preset/New-preset/Prev-preset/Next-preset. `g_lastModality` (mouse vs. gamepad) flips the edit-mode hint text (`EditHintText()`) between drag/hotkey phrasing and controller button prompts — deliberately the ONLY thing that changes visually per modality (toolbar buttons stay plain clickable text regardless, keeping the diff small; no custom Direct2D icon-glyph system). Voice entry into edit mode does NOT go through the LLM: it reuses the wake/sleep-word mechanism (`web/js/app/wake-word.js`) as a third, unconditionally-checked phrase (`overlayEditPhraseEnabled`/`overlayEditPhrase`, independent of hands-free mic state) that POSTs directly to a new `POST /api/overlay/edit-mode` (`app/api/overlay.py`), which no-ops for free if the overlay isn't running (same guard `overlay_process.push()` already has). Control hints are NOT drawn per-widget (a stray leftover from the first pass) — `RenderPlaceholder` only shows the widget name now; the single source of truth is `RenderControlsHint` at the bottom of the toolbar, which shows the dynamic hotkey text in mouse modality and real Xbox-style button glyphs (`DrawButtonGlyph`/`DrawGlyphChip` — colored circles for A/green, B/red, X/blue, Y/yellow, gray pills for LS/RS/LB/RB) in gamepad modality, reused identically in the exit-confirm prompt. Entering edit mode also steals OS foreground/focus (`SetActivatable` flips `WS_EX_NOACTIVATE` off on `g_configWin`, `SetForegroundWindow`+`SetFocus`, restoring the game's prior foreground window — `g_prevForeground` — on exit) so the game stops processing keyboard/mouse while you're editing; best-effort, same caveat as everything else here (a game reading raw/exclusive input ignores window focus).
- `app/prompts/*.md` — all system/task prompts as Markdown, loaded+cached by `app/core/prompts.py`. Edit prompts there, never inline in Python.
- **Narration vs. game audio** (`GET /api/system/audio-peak`, `app/api/system.py` → `get_peak_level()` in `app/services/system/app_audio.py`): reads the live Windows per-session peak meter (`pycaw`'s `IAudioMeterInformation`, `QueryInterface` on the session's `_ctl`) for whichever process `get_foreground_process_name()` currently reports — this is instantaneous, unlike the OCR-derived game-state `activity` label which lags ~15s behind reality and was rejected for this precisely because of that lag. `web/js/app/narration.js`'s `waitForGameQuiet()` polls this endpoint before each queued sentence starts playing (and before its overlay toast fires, so toast timing stays in sync) and only releases once the peak has stayed below `GAME_QUIET_PEAK_THRESHOLD` for `GAME_QUIET_HOLD_MS` — a short debounce so narration doesn't sneak into a brief quiet beat mid-dialogue-line — capped by `GAME_QUIET_MAX_WAIT_MS` so a game with constant ambient audio can't stall narration forever. A `null` peak (non-Windows, no foreground game, or no audio session for it) skips the wait entirely rather than adding a pointless delay to every sentence with nothing to gate against. Rejected alternatives: ducking the game's own volume during narration (independent of this, could still be layered on later) and gating on the OCR `activity` label (too stale — see above).

### Config flow (non-obvious)

The Settings UI persists changes via `persist_env_values()` writing back to `.env` AND mutates the live singleton (see `app/api/config.py`) — no restart needed. ### Latency-sensitive plumbing (2026-07-04 pass)
- `app/core/memory.py`, `observations.py`, `reminders.py` each keep a module-level in-memory cache of their JSON file (`_cache`/`_entries_cache`/`_pending_cache`), populated on first read and kept in sync by the store's own save function on every write — these files are read on every single chat turn (`_build_base_messages`) but were previously re-read+re-parsed from disk synchronously (blocking the event loop) every time. There is no other writer of these files at runtime, so the cache is always authoritative; a restored backup (`app/api/backup.py`) only takes effect after a restart anyway (fresh process, empty cache), same as `.env`/Settings. `game_state.py` already had its own equivalent (`_cached_values`) before this pass. **Tests that monkeypatch these stores' `*_PATH` constants must also reset the matching cache variable to `None` in the fixture**, or state leaks across tests (see `tests/test_memory.py`, `test_observations.py`, `test_reminders.py`).
- `_build_base_messages` (chat.py) — **only for Anthropic models** (`"claude"`/`"anthropic"` in `settings.openrouter_model`) — sends the system prompt as two content blocks instead of one string: a stable prefix (base prompt + custom instructions + sleep-word backstop + monitors) carrying an explicit `cache_control: {"type": "ephemeral"}` marker, and a variable suffix (datetime, foreground app, memories, reminders, game state, observations) with none. This is real prompt-caching for Anthropic via OpenRouter. **It is gated because it is NOT free elsewhere**: on Gemini (the default model) the `cache_control` breakpoint gave no benefit and could push OpenRouter into an explicit-cache-creation round-trip per turn, adding latency — worst in the multi-round tool loop (e.g. web search felt "much slower"). Non-Anthropic models get the plain concatenated string, exactly as before the caching pass.
- `system_companion.md` explicitly tells the model to batch multiple known-needed tool calls into one round rather than probing sequentially — each tool round is a full extra LLM round-trip in `_run_chat_with_tools`/`_stream_chat_with_tools` (chat.py), up to `MAX_TOOL_ITERATIONS = 8`.
- `llm/client.py`'s `get_client()` passes `timeout=45.0` to `AsyncOpenAI(...)` (previously unset, i.e. httpx's 600s default) — a hung/stalled upstream now fails in ~45s of read-inactivity instead of hanging the request for minutes. Per-network-operation (connect/read/write) timeout, not a hard cap on total streamed-response duration.
- `tts/kokoro.py` and `tts/chirp3.py` reuse one persistent `httpx.AsyncClient` (`_get_client()`) instead of opening a fresh one per call — narration fires a TTS call per sentence, so a multi-sentence reply used to pay a fresh TCP/TLS handshake per sentence. `openrouter_tts.py` already reused the shared OpenAI SDK client via `get_client("openrouter")`.
- `game_state_extraction.py`'s CPU-bound PIL work (`image.resize`, `image_to_b64`, `_visual_diff_percent_sync` via the async `_visual_diff_percent` wrapper) runs via `asyncio.to_thread` — it was running inline on the event loop inside `_capture_tick`, which ticks every capture interval while a game is tracked and could stall a concurrent foreground chat request's I/O.
- Deliberately NOT done: real TTS network streaming (playback starting before synthesis fully completes) — see the TODO.md entry for why and what it would require.

### Memory model (three scopes + observations journal)
Flat JSON list in `data/memory.json` with an **explicit `scope` field** (`user`/`game`/`session`; pre-scope entries migrated on read), injected into every system prompt with scope suffixes. ALL writers must go through `memory.remember(content, scope, process, session_id)` — it owns scope resolution and the degradation rule (unresolvable game/session scope degrades to **user**, never to a different game tier). Writers: chat tools + the per-exchange extraction pass (exists because models can't be trusted to call memory tools proactively). The OCR game-state pass does NOT write memory — it appends to the observations journal (`app/core/observations.py`, per-session staging, capped), and the extraction pass promotes corroborated observations. `saved_at` is never updated on edit — the crash-rollback tool depends on it. UI: user scope = Personal Data modal; game/session scope + observations = Gaming Journal modal (which also hosts the Game Awareness settings, moved out of Settings — its awareness inputs save via the shared `saveSettings()` in `web/js/app/settings.js`).

A `user`-scope fact stated before a game was ever tracked (e.g. playtime mentioned in passing) can't be placed more specifically at save time — `remember()`'s degradation rule has no session/process to anchor to yet. `app/services/llm/memory_retagging.py` catches this: hooked into the same `game_state.start_tracking()` call site as `schedule_bootstrap` (`app/services/llm/game_state_extraction.py`), it runs once per process per app run the moment that game starts being tracked, reviewing standing `user` facts and moving the ones specifically about it into `game`/`session` scope via `memory.update_memory` (preserves `saved_at`, unlike remove+re-add).

`format_memories_for_prompt()`'s scope filter (`app/core/memory.py`) must run even when `active_process` is `None` — it used to skip filtering entirely in that case (`if active_process is not None:` guarding the whole thing), which meant with no game tracked the LLM was fed every game/session-scoped memory from every game ever played, not just user-scope facts. Fixed 2026-07-04: when no process is active, only entries with no `process` are included. Mentioning a game you're not actively playing (not tracked/whitelisted) correctly stays `user`-scope by design — that's not a bug, see the extraction prompt's rule in `app/prompts/memory_extraction.md`.

`extract_and_apply_memory()` (`app/services/llm/memory_extraction.py`) is scheduled fire-and-forget per chat turn (`_schedule_memory_extraction` in `chat.py`) without awaiting the previous turn's pass. Two quick consecutive turns used to both read `known_facts` before either had written its save, so both saved the same fact worded slightly differently — the exact-string dedup in `remember()` only catches identical wording, not near-duplicates. Fixed by wrapping the pass body in a module-level `asyncio.Lock()` so passes serialize and each one's `known_facts` reflects every earlier turn's completed write.

`_save_via_remember()`'s (`app/services/llm/tools.py`) degradation note to the model must read as final, not as a retriable failure. It used to say "requested {scope} scope wasn't available" when `save_session_memory`/`save_game_memory` degraded to `user` (no game/session tracked) — the model read that as something to fix, called `remove_memory` on the id it just got back, then retried the identical `save_session_memory` call, got the same note, and looped remove→save→remove→save until `MAX_TOOL_ITERATIONS` (8) was exhausted with zero reply text, surfacing as the "stuck juggling tools" fallback (chat.py:454/504). Fixed 2026-07-04: the note now explicitly says "this is final, do not retry or remove it." Any other tool-result string fed back to the model should get the same scrutiny — anything that reads like an error/unavailability invites a retry loop instead of being accepted.

### Frontend conventions
Every `fetch()` in the frontend (`web/js/app/*.js`) must send the `x-lyko-token` header (or `?token=` for `<img>`/`<audio>` src URLs) or it breaks in the desktop app while appearing fine under dev uvicorn.

**No native browser chrome — use the themed primitives.** Never call `alert()`/`confirm()`/`prompt()`, and don't rely on native `title` tooltips or the native `<select>` popup list.
- Dialogs: `showConfirm(msg, {title, danger, confirmText})` → `Promise<bool>` and `showAlert(msg, {title})` → `Promise<void>` (both in `core.js`, awaited at every call site). CSS `.dialog-*`.
- Tooltips: the `.help-tooltip` handler in `core.js` now themes ANY element carrying a `title` attribute (lazily migrated to `data-tip` on hover, so setting `.title = ...` in JS still works) in addition to `.cfg-help[data-tip]`.
- Selects: `web/js/app/custom-select.js` (loaded right after `core.js`) progressively enhances every `select:not([size]):not([multiple])` — the native `<select>` stays the source of truth (all `.value`/`change`/option-population JS untouched), visually hidden behind a themed `.cs-trigger` + a body-appended `.cs-panel` (so the modal's `overflow:auto` can't clip it). Sync is three-way: native `change` event, a per-select MutationObserver on options+`disabled`, and instance-level intercept of the `value`/`selectedIndex` setters (for programmatic `.value =`, which fires no event). Theme a dynamically-built select on demand via `window.enhanceSelect(el)`. Deliberately still native: OS file pickers and the `datetime-local` calendar popup (see `TODO.md`).

### In-app YouTube player (2026-07-04)
`play_on_youtube` (`app/services/llm/media_tool.py`) no longer opens a browser tab — it resolves a video id (yt-dlp for general search, ytmusicapi for `prefer_audio` songs) and returns it as a `{"video_id", "title"}` payload, which `_execute_tool_impl` (`app/api/chat.py`) wraps into a `{"type": "youtube_play", ...}` side effect (same plumbing as `volume`/`stop_listening`/`tool_sfx`): forwarded as SSE `youtube_play` in both `/stream` and `/voice/stream`, or as `ChatResponse.youtube_play` in the non-streaming paths. `control_youtube_player` (play/pause/restart/next/previous/stop/set_volume) is the same pattern via `youtube_control` — a dict now (`{"action", "volume"?}`, not a bare string) so `set_volume` can carry its 0-100 level alongside the action. Frontend: `web/js/app/youtube-player.js` — a floating, draggable panel (`.floating-panel`, default bottom-right, position persisted at `lyko-youtube-panel-pos`, mirrors `game-state.js`'s panel exactly) hosting a real YouTube IFrame Player (`https://www.youtube.com/iframe_api`, loaded lazily on first use). `window.loadYoutubeVideo(videoId, title)` and `window.controlYoutubePlayer(action, volume?)` are the entry points `chat-stream.js`/`voice.js` call on the respective SSE/response fields. `next`/`previous` walk a local `ytQueue` (every video played this session) — there's no real YouTube playlist involved. The video's own volume (`set_volume`) is entirely separate from `set_narration_volume` (the companion's spoken voice) — the system prompt spells this out explicitly because the model conflated the two on first testing ("play it at half volume" was misread as the narration tool). **`stop` hides the panel and fully unloads the player (`stopVideo()`), which is not the same as pausing** — a later `play`/`restart` therefore always re-shows the panel itself (not just toggling playback) and the video restarts from 0:00, since YouTube's own `stopVideo()`→`playVideo()` doesn't resume — this was a real bug (audio played with the panel gone) until `controlYoutubePlayer`'s `play`/`restart` cases were made to call `showYoutubePanel()` again. **The mount div gets replaced, not filled**: the IFrame API replaces its target element with the `<iframe>` itself, so the mount point (`#youtube-player-frame-mount`) is wrapped in a separate `.youtube-player-frame` div that owns the aspect-ratio/background CSS — don't collapse that wrapper, styling the mount directly would vanish the moment the player initializes. Known caveat, not fixed: `playerVars.autoplay: 1` on a freshly-loaded iframe can still hit the browser's autoplay-without-mute block depending on this origin's media engagement; the IFrame API's own UI shows a click-to-play thumbnail in that case, so it degrades to one manual click rather than failing silently. Deliberately out of scope: pushing this into the native overlay (would need a new opaque WebView2 popup window in `overlay/overlay.cpp`, separate from and much larger than this).

### YouTube account OAuth + playlists (2026-07-04)
`app/core/youtube_auth.py` + `app/api/youtube_oauth.py` mirror Spotify's PKCE OAuth flow (`spotify_auth.py`/`spotify_oauth.py`) almost exactly, with one real difference: **Google's token endpoint still requires the Client Secret** in both the initial exchange and every refresh — Google's own installed-app docs say it isn't treated as fully confidential in that context, but the API call rejects without it regardless, so unlike Spotify (Client ID only) this needs `settings.youtube_client_id` AND `settings.youtube_client_secret` (Settings → API Keys → YouTube, the Secret stored/cleared the same way as IGDB's). **The Google Cloud OAuth client MUST be type "Web application", not "Desktop app"** — Desktop app clients don't expose an Authorized-redirect-URIs field at all in the Console UI, so a custom path like `/api/youtube/oauth/callback` can't be registered on one (the initial Settings hint wrongly said "Desktop app" and had to be corrected). Registering the right *host* also matters and is easy to get wrong: `_redirect_uri()` builds the callback URL from the incoming request's own `request.base_url`, which is whatever host the browser/webview actually used — the desktop app (`run_app.py`) always loads via `http://localhost:{PORT}` (never `127.0.0.1`, see its `URL` constant), so a user who registers only `127.0.0.1` in the Google Console and connects from the desktop app gets `Error 400: redirect_uri_mismatch` in the OAuth screen even though everything else is configured correctly. Settings now tells users to register both `127.0.0.1` (dev uvicorn opened directly) and `localhost` (desktop app) variants of the callback URL if unsure which they'll use. The OAuth `/start` call also passes `access_type=offline&prompt=consent` — without `prompt=consent`, Google only issues a `refresh_token` on a user's very first-ever consent for that Client ID, so a Settings→Disconnect→Connect cycle would otherwise silently get an access-only grant that can't be refreshed. Scope is `youtube.readonly` — enough to list/read playlists, but there's no YouTube equivalent of Spotify's remote-playback API, so playlist "playback" is just queuing every video into the existing in-app player (`app/services/llm/youtube_playlist_tool.py`'s `play_youtube_playlist` fetches the playlist's videos and returns them as a `{"videos": [...], "title"}` payload, forwarded as the `youtube_playlist` side effect/SSE event exactly like `youtube_play`/`youtube_control`). `_find_best_match` does simple substring/word-overlap matching against playlist titles — no fuzzy-matching dependency, good enough for "my road trip playlist" against "Road Trip 2024". `window.loadYoutubePlaylist(videos, title)` (`youtube-player.js`) extends the same local `ytQueue` a single `play_on_youtube` video would, so `next`/`previous` walk the real playlist once one is loaded.

### Sound effects (cosmetic, client-side only)
`web/js/app/sfx.js` synthesizes short SFX via the Web Audio API (`playSfxNote`/`playSfxSweep` + `playSentSfx`/`playToolSfx`, near the pre-existing mic `beep()`/`playWakeChime()`) — no audio asset files. Gated by `sfx_enabled` (mirrors `narrate_enabled`: `Settings.sfx_enabled` → `app/api/config.py` GET/PUT → `#cfg-sfx-enabled` checkbox), unlike the mic beeps which are unconditional functional feedback. `_execute_parsed_tool_calls` (`app/api/chat.py`) appends a `{"type": "tool_sfx", "name": <tool name>}` side effect for **every** tool call (in addition to any real side effect like volume/stop_listening), forwarded as SSE `tool_sfx` in both `/stream` and `/voice/stream`; the frontend's `TOOL_SFX` map picks a specific sound (web search, memory save/delete) or falls back to a generic click. The non-streaming path ignores the unknown side-effect type harmlessly.

### Backup / restore
`app/api/backup.py`: `GET /api/backup/export` zips `data/` (excluding `webview_profile/`, `debug_log.json`, `crash_log.txt`) plus `.env` into a downloadable archive; `POST /api/backup/import` extracts one back over the project root (zip-slip guarded, only accepts `.env`/`data/*` entries). Settings from an imported `.env` only take effect after a restart — import does not touch the live `Settings` singleton.

## Gotchas

- **Sentence-splitting must treat a complete `![alt](url)`/`[label](url)` as atomic, not just while it's still streaming in.** `extractCompleteSentences` (`web/js/app/chat-stream.js`) already held back an *unfinished* markdown link/image at the end of the buffer, but once the pattern fully arrived, the plain `.!?`-based scan could still find a boundary punctuation mark inside the alt text/label itself (e.g. an image titled "...background. Love ...") and split the sentence mid-pattern. The resulting fragment (missing its closing `]`/`(url)`) no longer matches `stripMarkdownForNarration`'s regex in `narration.js`, so the raw fragment — including part of the URL — got sent to TTS and narrated aloud. Fixed 2026-07-04: the scan now skips over any complete `!?[...](...)` span atomically via a sticky regex (`MARKDOWN_LINK_RE`) before considering it for sentence boundaries.
- **`show_image`/`/api/proxy/image` headers must stay identical between validation and render fetch.** `web_search_tool.py`'s `_image_candidate_loads` validates a candidate image URL server-side (headers = its `SEARXNG_HEADERS`: UA + Accept-Language, no Referer) before handing it to the model; the browser's `<img>` then re-fetches that same URL later through `main.py`'s `proxy_image` for actual display. If the two fetches use different headers, a candidate that passed validation can still 403 at render time — some hosts' hotlink protection allows a referer-less request but blocks a third-party `Referer` (e.g. `google.com`), which `proxy_image`'s headers used to add unconditionally. This is why some images (e.g. "cat") showed fine while others (e.g. "heart") rendered as `[image unavailable: ...]` — it depended on that specific host's policy, not a general proxy bug. Fixed 2026-07-04: `_PROXY_HEADERS` now spreads `SEARXNG_HEADERS` (imported from `web_search_tool.py`) instead of its own divergent header set. Keep them unified if either is touched again.
- **Overlay build (`overlay/build.cmd`)**: two traps hit before. (1) MSVC rejects a **function-local `struct` with a default member initializer that references a function-local `enum`** (`error C2065: 'PkText' undeclared` in the generated ctor) — declare such enum+struct pairs at namespace scope, not inside the function. (2) A stray `"` anywhere in the machine's `PATH` makes `vcvars64.bat` abort with `"... was unexpected at this time."` — `build.cmd` now strips quotes from PATH defensively, so don't remove that line. `RUN.cmd` rebuilds the overlay every launch (non-fatal on failure). Libs are pulled via `#pragma comment(lib)` in `overlay.cpp`, not the link line.
- **Gamepad input can't be given to the overlay exclusively.** Focus-stealing (`SetActivatable`+`SetForegroundWindow` in `ApplyEditMode`, see above) only redirects keyboard/mouse, which Windows routes by focus. XInput doesn't work that way — `XInputGetState()` is a raw poll of the physical device, and every process polling it (the game and the overlay's `PollGamepad`) sees the identical state regardless of focus/foreground. There's no Win32 API for per-process controller exclusivity; the real fix (a virtual-controller driver like ViGEmBus, à la Steam Input/DS4Windows) was deliberately deferred as too large a dependency for now — documented as a known limitation in `overlay/README.md`, not silently "fixed."
- `.env` at repo root is the user's real config with live API keys — never overwrite it wholesale; settings changes go through `persist_env_values()`.
- `winrt-*`, `windows-capture`, `pycaw` imports are Windows-only; modules using them import lazily/guarded so the server still boots elsewhere.
- Background LLM passes (memory extraction, game-state extraction) are fire-and-forget asyncio tasks — they must never add latency to or raise into the visible reply path. The game-state pass is vision-grounded: it receives each poll window's first/last frames as screenshots, and self-maintains a per-game UI-decoding notes document via its `training_data_update` output (there is no separate trainer model/pass).
- `TODO.md` is the maintained backlog of open items; check it before proposing work.
- Voice transcript extraction (raw-audio mode): the main model prefixes replies with a `<transcript>` block, peeled by `_peel_transcript` in `app/api/chat.py`; delivered only in the final `done` SSE payload. Text chat paths must peel/discard it too — models emit it out of habit after voice turns.
- "Reply freezes mid-stream" had TWO causes, both fixed — keep both guards when touching streaming code: (1) any `renderChatLog()` during streaming (chat switch) wipes `chatLog` and detaches the live bubbles; the stream loops re-attach via `assistantEl.isConnected` checks + a tail re-render. (2) The REAL "whole app hangs" bug: `extractCompleteSentences` used a catastrophically backtracking regex (`(?:[^.!?\n]+|[.!?](?!\s))*(...)`) — one `exec()` on a long incomplete sentence took minutes and froze the JS main thread (UI dead, all polling stops, window only closable via X). It is now a linear scan; NEVER split streaming text with a backtracking regex. Diagnosis tell: uvicorn console request logs going silent while the process lives = frontend JS wedged, not the server.
- "UI element missing but the API is polling fine" — check localStorage-persisted UI state first (`lyko-game-state-panel-pos`, `GAME_STATE_CLOSED_KEY`): the floating panel's position/closed state persist across reloads and can leave an element unhidden yet off-screen. `web/index.html` + `web/js/app/*.js` can be exercised headlessly with jsdom (see the scratchpad repro pattern: stub `fetch` per route, eval the app scripts in load order, assert on DOM).
- Tool-round boundary in `_stream_chat_with_tools` (`app/api/chat.py`): the `"\n\n"` separator delta must be yielded the moment a text-bearing round ENDS (right before its tool calls run), not lazily deferred until the next round's first text delta shows up. Deferring it left a round's trailing sentence ("Let me check that...") stuck un-narrated in the frontend's `sentenceBuffer` remainder for as long as the tool call took — or forever, if the next round turned out to be tool-only with no text. Also, models tend to restate the pre-tool-call text as a second paragraph once the tool result comes back — the system prompt now has an explicit line telling it to continue instead of re-greeting.
- **In-game overlay: FULLY REVERTED after 7 failed rounds (2026-07-03) — read this before ever re-attempting it.** A pywebview/WebView2-based overlay (extra frameless windows drawn over the game) is a dead end; every mechanism was tried and disproven on-machine: (1) pywebview 6.2.1's `transparent=True` never makes the WinForms form transparent — only the WebView2 control's `DefaultBackgroundColor` (confirmed in its installed source) — so the page's transparent pixels show an opaque gray form, and no exstyle/DWM permutation on top can fix it; (2) bare `WS_EX_LAYERED` stops a window rendering at all until `SetLayeredWindowAttributes`/`UpdateLayeredWindow` commits it; (3) color-key done correctly (`LWA_COLORKEY` via ctypes) → black window after a split-second flash: Chromium's GPU compositor cannot render into a layered window at all — rules out ALL alpha/color-key approaches; (4) `SetWindowRgn` region clipping returns success but is visually inert — WebView2's DirectComposition content ignores GDI window regions; (5) setting WinForms `Form.TransparencyKey` OR `Form.Region` on a pywebview window deadlocks the entire app at boot (shared UI thread; only raw win32 via ctypes is safe); (6) fit-to-content window resizing (the last WebView2-shaped idea) was implemented but reverted with everything else, untested. If the overlay is ever rebuilt, start directly at: native layered windows drawn with GDI+/Direct2D via ctypes + `UpdateLayeredWindow` per-pixel alpha (software-rendered — exempt from the GPU limitation; how real game overlays work), or resurrect the fit-to-content approach from git history (`4957a50`, reverted). Exclusive-fullscreen games bypass any of this regardless — only borderless/windowed can ever show an overlay.
