# CLAUDE.md

Guidance for Claude Code in this repo. Keep this file under ~80 lines: prune stale detail before adding new detail.

## Standing workflow (user-mandated)

1. Read this file first before any task.
2. Capture mistakes/corrections here immediately so they can't recur.
3. Keep this file current toward: no re-exploration after context loss, minimal tokens, under ~80 lines.
4. After finishing a task, update `TODO.md` (remove done items, add newly found ones).
5. After each task, commit and push to `main` (pre-authorized — don't ask).
6. Never start servers, curl endpoints, or write one-off verification scripts — user tests everything. `pytest tests` is allowed. Never run `overlay/build.cmd` — `RUN.cmd` already rebuilds it on every launch.

## What this is

Lykompanion — local, voice-first gaming companion. FastAPI backend + vanilla HTML/CSS/JS frontend (no build step). LLM calls go through OpenRouter (or Google AI Studio / any OpenAI-compatible endpoint). Windows-only for OCR/WGC/per-app volume. [README.md](README.md) has feature behavior, config vars, API/tool tables — check it before reading code.

## Commands

```bash
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 6692 --reload  # dev server
.venv\Scripts\python.exe -m pytest tests                                                 # tests
.venv\Scripts\python.exe -m pytest tests/test_memory.py -k test_name                      # single test
```
No linter/formatter configured. `RUN.cmd`/`run_app.py` = desktop app (pywebview/EdgeWebView2, frameless window with its own JS-driven titlebar drag/resize/snap — see `init.js`/`run_app.py` if touching window chrome; dev uvicorn has no auth, desktop app enforces `LYKO_API_TOKEN` on `/api/*`).

## Search hygiene

`data/` (~12k runtime files) and `.venv/` dominate unscoped searches — scope to `app/`, `web/`, or `tests/`. Frontend is `web/js/app/*.js`, 14 ordered classic `<script>` files (not ES modules) sharing one global scope, loaded in dependency order by `index.html` (core.js first, init.js last). Grep function names/DOM ids there first. Largest files: `settings.js`/`game-state.js` (~700ea), `style.css` (~1900), `index.html` (~800), `chat.py` (~500).

## Architecture

Request path: `chat-stream.js` → `/api/chat/stream` (SSE) or `/api/chat/voice[/stream]` (raw audio) → agentic tool loop → sentence-by-sentence TTS narration.

- **Tool loop** (`app/api/chat.py`): `_run_chat_with_tools`/`_stream_chat_with_tools` re-call the model up to `MAX_TOOL_ITERATIONS=8`. Add a tool: new `app/services/llm/<name>_tool.py` with `*_TOOLS` spec + `execute_*`, wire into `ALL_TOOLS`/`_execute_tool_impl`, document in README (memory tools live in `tools.py` instead).
- `app/api/*` route handlers; `app/core/*` settings + one-JSON-file-per-store persistence (no DB); `app/services/llm/*` client + tools + background passes (`memory_extraction.py`, `game_state_extraction.py` OCR poller); `app/services/tts|screenshot|ocr|system` provider backends (`capture.py` GDI vs `wgc_capture.py` WGC for the OCR poller, to avoid game stutter).
- **Native overlay** (`overlay/overlay.cpp`, C++, not Python): layered-window + Direct2D exe, own named-pipe API (`\\.\pipe\lykompanion-overlay`). Python (`overlay_process.py`) is a thin client only — spawn/quit/push toasts. Full details in `overlay/README.md` + `TODO.md`. Do not rebuild it yourself (see workflow #6).
- `app/prompts/*.md` — all prompts live here, loaded via `app/core/prompts.py`; never inline in Python.
- Config: `app/core/config.py`'s `Settings` singleton; Settings UI writes `.env` via `persist_env_values()` AND mutates the live singleton — no restart needed. Per-feature model/provider fields default to `""` = inherit main setting.
- Memory: `data/memory.json`, scoped `user`/`game`/`session`. All writers go through `memory.remember()` (owns scope-degradation rule: unresolvable scope degrades to `user`, never cross-game). OCR pass writes to the observations journal instead (`app/core/observations.py`); extraction promotes corroborated observations into memory.
- Modpack variants (2026-07-06): a session record may carry `variant` (modpack name, e.g. Nolvus). Detected at game launch by `variant_detection.py` (window title/cmdline/parent → 1 LLM call; also fixes javaw-style junk titles via `fetch_art(search_term=)`), OCR fallback = `modpack` field in extraction. Game memories may be variant-tagged (`remember(variant=)`, shown only while that pack's session is active) — **tagging is automatic, not an LLM judgment call** (2026-07-12): every game-scope save while a modpack session is active gets that variant stamped unconditionally (was a `modpack_specific` boolean the extraction/chat model had to classify per-fact; too unreliable — e.g. StoneBlock facts kept landing as "universal Minecraft"). Reclassify a mis-scoped one via its variant chip in the Gaming Journal (Universal Info tab also has a variant filter row now). Training data keys `process::variant`, editable per-variant in the Gaming Journal's Training Data tab (`GET/PUT .../training-data/{process}?variant=`, `own` flag = has its own doc vs falling back to base); pack knowledge seeded by `schedule_variant_bootstrap`. Trackers stay per-process. **The base-game bootstrap (`schedule_bootstrap`) is triggered from inside `variant_detection.py`'s `_detect_and_apply` (its `finally` block), not from `_capture_tick` directly** — scheduling both at once raced (bootstrap reads the display title synchronously at task start, before detection's async title-fix could land), so a generic host exe like `javaw.exe` reliably got bootstrapped under "Javaw" instead of the corrected "Minecraft."
- Anthropic models get real prompt-caching (`_build_base_messages` splits system prompt into cached prefix + variable suffix) — gated to Claude only, `cache_control` hurt latency on Gemini via OpenRouter.
- `app/core/memory.py`/`observations.py`/`reminders.py`/`game_state.py` keep in-memory caches of their JSON files — tests that monkeypatch their `*_PATH` constants must also reset the matching cache var to `None`.

## Frontend conventions

Every `fetch()` must send `x-lyko-token` (or `?token=` for `<img>`/`<audio>` src) — otherwise fine under dev uvicorn but breaks in the desktop app. No native browser chrome: use `showConfirm`/`showAlert` (core.js) instead of `alert`/`confirm`/`prompt`; selects are auto-themed by `custom-select.js`; tooltips via `title`/`data-tip` are auto-themed by `core.js`.

## Gotchas

- Prompt edits (`app/prompts/*.md`) need an app restart — `load_prompt` is `@lru_cache`d, unlike Settings which apply live. Tell the user to restart when they test a prompt change.
- **Mic input dropping consonants (e.g. "What's" losing its "t's") was Chromium's WebRTC `echoCancellation` pipeline** (2026-07-05) — it bundles a transient/click suppressor meant to filter keyboard-typing noise during calls, which reproducibly misfires on short unvoiced plosive/fricative sounds (t, k, p, s). Found only after ruling out (in order): Bluetooth/wireless-dongle duplex issues, WebView2-hosting quirks (repro'd identically via dev-server-in-a-plain-browser-tab, which pointed back at our own code/constraints), and a real but separate bug (see below). `core.js`'s `micAudioConstraints()` now has `echoCancellation: false, noiseSuppression: false, autoGainControl: true`. Losing AEC trades away `narration.js`'s barge-in protection against speaker bleed-through false-triggering an interrupt — accepted, since dropped consonants corrupt every recording. `autoGainControl` must stay on: the hands-free VAD gate (`voice.js`'s `computeAmplitude > vadThreshold/127`) is calibrated assuming AGC-normalized levels.
- Separately: the ScriptProcessorNode→AudioWorkletNode migration (fixing main-thread-jank capture drops) needs `channelCountMode: "explicit"` on the `AudioWorkletNode` in `voice.js`'s `startLiveMic()` — the default `"max"` mode does NOT downmix a stereo capture device to mono before `process()`, silently discarding channel 1 (`mic-worklet-processor.js` only reads `inputs[0][0]`), unlike the old `createScriptProcessor(4096, 1, 1)` which forced true mono.
- **Kokoro TTS misreads ALL-CAPS 2-3 letter gaming acronyms as chemical formulas** (HP→"Hydrogen Phosphorus", etc). Fixed client-side via `narration.js`'s curated `GAMING_ACRONYM_FIXES` map (dots the letters before TTS) — extend the map, don't switch to a general heuristic (would mangle Roman numerals in game titles).
- Sentence-splitting (`chat-stream.js`'s `extractCompleteSentences`) must treat a complete `![alt](url)`/`[label](url)` as atomic via `MARKDOWN_LINK_RE`, or punctuation inside alt text splits mid-pattern and leaks a raw URL fragment into narration. Also: NEVER use a backtracking regex there — one froze the JS main thread for minutes (tell: server logs go quiet while process lives = frontend wedged, not backend).
- `show_image`/`/api/proxy/image` must use identical headers to `web_search_tool.py`'s `SEARXNG_HEADERS` for both validation and render fetch, or some hosts' hotlink protection 403s only at render time.
- Overlay build traps: MSVC rejects a function-local struct default-init referencing a function-local enum (move to namespace scope); a stray `"` in PATH breaks `vcvars64.bat` (build.cmd strips quotes — keep that). `overlay/Lykompanion-overlay.exe` dirtied the diff on every rebuild even with unchanged source (link.exe stamping a build timestamp into the PE header) — first fixed via `/Brepro` on the `cl`/`link` lines in `build.cmd` (2026-07-05), but the exe is no longer committed at all as of 2026-07-05: it's now gitignored (`overlay/.gitignore`'s plain `*.exe`, no more force-track negation) and untracked from `main`. Users without VS Build Tools will need to build it themselves or fetch a release artifact — this reverses the earlier "ship the prebuilt exe" decision on the user's explicit instruction.
- Gamepad input can't be given to the overlay exclusively — `XInputGetState()` is a raw device poll, no per-process exclusivity API exists (would need ViGEmBus). Documented limitation, not a bug to fix casually.
- `.env` has live API keys — never overwrite wholesale; go through `persist_env_values()`.
- `winrt-*`/`windows-capture`/`pycaw` imports are Windows-only and import lazily/guarded.
- **Every `WindowsCapture` instance leaks** (2026-07-06, was 15GB+ RSS after play): its `__init__` passes bound methods to the Rust-side `NativeWindowsCapture`, forming a cycle CPython's GC can't traverse (native object lacks tp_traverse). `wgc_capture.py`'s per-tick capture must keep its finally-block that detaches the frame handlers and empties the result dict, or each leaked cycle pins a ~33MB full-res frame copy. Long-term fix idea in TODO.md.
- Background LLM passes (memory/game-state extraction) are fire-and-forget — must never add latency to or raise into the reply path.
- **Game-state extraction's LLM call used to be directly `await`ed inside `_capture_tick`, which the poller's own loop awaits — no longer true as of 2026-07-13, see below.** (2026-07-06) A 429 there let the OpenAI SDK's default retry logic sleep the full upstream `Retry-After` (observed 60s) *inside* that await, freezing the whole OCR poller (no captures, no tracking) for over a minute. Originally fixed via `client.py`'s `get_client()`/`chat_completion(max_retries=)` param — extraction passed `max_retries=0` (fail fast); that override was later removed once the call stopped blocking the loop (see below), so it now gets the SDK default retries like other call sites. Other background passes (memory extraction, variant detection, bootstrap) are true `asyncio.create_task()` fire-and-forget, so they were never affected.
- **A poll window can span an arbitrarily long absence, not just ~5s, because `_capture_tick` returns early (untouched) whenever the tracked process isn't foreground — alt-tab away for 5 minutes and the window timer just keeps counting, silently.** (2026-07-13) Observed: a 299s-old window closed the instant focus returned, diffed against an ancient frame, then a second window closed 9s later right behind it — two rapid-fire calls that tripped `xiaomi/mimo-v2.5`'s native provider's own abuse detector (`"risk_control"`, HTTP 400, distinct from and worse than a plain 429 - it's "you're behaving like abuse," not "try again later"). Fixed by tracking `_last_tick_at` (updated only on ticks that actually reach the capture step) and resetting the window from scratch if the gap since the last tick exceeds the configured poll interval, instead of closing/diffing a window that spans the whole absence. Separately: pinning provider routing to a single upstream (done to fix uptime — see the "no banner"/provider-routing conversation) concentrates ALL request volume, including SDK retries, onto that one provider — worth spreading across 2+ reliable providers rather than pinning to exactly one if this recurs.
- **Even at `max_retries=0`, a normal (non-429) call still took 3-70+s in practice (`data/debug_log.json`), and awaiting it inline meant the overlay's game-state panel only updated every `poll_interval + call latency`, not every `poll_interval` as configured** (2026-07-13, confirmed fixed live). Fixed by backgrounding the call: `_capture_tick` now dispatches `_run_structuring_pass` via `asyncio.create_task` instead of awaiting it, so capture/OCR keeps ticking at full cadence regardless of call latency. `_extraction_in_progress` (a set of in-flight process names) stops a second call from stacking on the SAME process while one's still running — the window just extends until it clears — while a different process is free to run concurrently. The overlay push is skipped if the tracked process changed while the call was in flight (avoids flickering stale data over whatever's now active). Follow-up same day: backgrounding this call also obsoleted `_call_extraction`'s `max_retries=0` (it existed only because this call used to block the poller's own loop) — a heavily-used/rate-limited `GAME_STATE_MODEL` (observed: `xiaomi/mimo-v2.5` 429ing repeatedly) was failing every window outright instead of retrying, so real updates only landed on whichever window got lucky. Removed the override; the SDK default retries (2, see `client.py`'s `get_client`) now apply like every other call site.
- Voice raw-audio replies prefix a `<transcript>` block, peeled by `_peel_transcript` (chat.py) — must be peeled on text paths too.
- Tool-round boundary in `_stream_chat_with_tools`: the `"\n\n"` separator must be yielded the instant a text round ends (before its tool calls run), not deferred to the next round's first delta, or a trailing sentence gets stuck un-narrated.
- **Google AI Studio + streaming tool calls: two real bugs found via `data/debug_log.json`, both in the delta accumulators (`_stream_chat_with_tools` in chat.py, `stream_chat_completion_deltas` in client.py).** (1) Gemini attaches `extra_content.google.thought_signature` to each tool call and rejects a later request replaying one without it — non-streaming preserved it for free (SDK models are `extra="allow"`), streaming now captures/replays it via `getattr(tc, "extra_content", None)`. (2) Gemini's OpenAI-compat layer sometimes reuses the same delta `index` for two different parallel tool calls in one round (each still has its own `id`) — keying strictly by index smashed both into one fake call (e.g. `play_youtube_playlistshow_image` with concatenated JSON args), which the model never requested and Gemini then rejects on replay. Fixed by falling back to `tc.id` as the accumulator key when a new id shows up on an already-populated index.
- Hands-free live mic capture (`voice.js`) uses an `AudioWorkletNode` (`mic-worklet-processor.js`), not `ScriptProcessorNode` — the latter's callback ran on the main thread and could be delayed/skipped by jank there, silently dropping chunks of captured audio mid-utterance. Don't regress back to ScriptProcessorNode.
- Chirp3 HD narration can pop mid-sentence — confirmed not a bug here (one API call per sentence, no server-side chunking/concatenation, WAV wrapping in `chirp3.py` is correct); it's a known artifact of the Chirp3 HD model itself. `app/services/tts/__init__.py`'s `_postprocess()` does peak normalization (consistent loudness across providers/voices) plus fade-in/out on every provider's output. **A single-sample impulse-declick pass was added and then reverted (2026-07-05)** — same failure mode as the WebRTC transient/click suppressor below: it misfired on legitimate high-frequency speech content (fricatives/sibilants are naturally large sample-to-sample swings, not clicks), producing audible static instead of removing pops. Don't re-add sample-level spike detection to narration post-processing without a much narrower/safer heuristic.
- **Maximized frameless window showed a faint desktop-colored gap at edges/corners** (2026-07-05) — Win11 rounds top-level window corners (`DWMWA_WINDOW_CORNER_PREFERENCE`) by default; our maximize is a JS snap-to-workarea (`init.js`), not native `WindowState=Maximized`, so the OS never suppresses rounding. Fixed in `run_app.py`'s `_remove_window_border()` by setting attr 33 to `DWMWCP_DONOTROUND`. Same function's DWM attr 34 (`DWMWA_BORDER_COLOR`) recolors the default white/accent window outline to match CSS `--accent` (`0x00BBGGRR` COLORREF, byte-swapped from the hex) — user wants the outline kept, just not white.
- **In-game overlay via pywebview/WebView2 is a dead end — fully reverted (2026-07-03), do not re-attempt.** WebView2's Chromium compositor cannot render into a layered/transparent window by any mechanism tried (transparent color, `WS_EX_LAYERED`, color-key, region clipping) — the GPU compositor ignores all of them. If rebuilt, start from native layered windows + GDI+/Direct2D via ctypes + `UpdateLayeredWindow` (software-rendered, how real overlays work) — see the current native `overlay/` for exactly that. Exclusive-fullscreen games bypass any overlay regardless.
- `debug_log.py`'s `record_request`/`_track` (client.py) only fire on a successful provider call — a raised exception (e.g. a 400) used to leave zero trace. `client.py`'s four `create()` call sites now wrap the call in try/except and call `debug_log.record_error()` (same ring buffer/disk file, `error` field instead of `reply`) before re-raising, so failed calls are now visible in the Debug panel/`data/debug_log.json` too. **That wrap still had a blind spot** (2026-07-13): the two non-streaming sites' `response.choices[0]` access sits AFTER the try/except, so a "successful" (200) response with `choices: null` (observed: a provider's abuse/risk-control system responding this way under load) crashed with a bare, unrecorded `TypeError` instead of a clean, logged error. Fixed via a shared `_first_choice()` guard used by both `chat_completion` and `chat_completion_message`.
- SearXNG web search (`web_search_tool.py`) fetches+extracts full page text (`trafilatura`) for the top 3 results instead of trusting SearXNG's one-line snippet — snippets were too shallow for specific questions. Falls back to the snippet per-result on fetch/extraction failure. Category param is `"web"` (some SearXNG versions renamed `"general"` → `"web"`; revert if your instance is old enough to need the old name).
- **A game not sold standalone on Steam (Minecraft Java, via `javaw.exe`) got mistitled "Minecraft Dungeons" with its cover art** (2026-07-13) — `game_art.py`'s `fetch_art()` has an LLM-resolved-title retry path (used when the exe name alone doesn't match anything) that searched Steam for the resolved title ("Minecraft") but, unlike the sibling `search_term`-trusted path a few lines above, never validated the result with `_titles_match` — so Steam's best real fuzzy match ("Minecraft Dungeons," a different actual game) got accepted unchecked. Deterministic, not flaky: delete-and-re-add reproduced the identical wrong result every time. Fixed by applying the same `_titles_match` guard to that retry. A process already mistitled from before the fix needs its `data/game_art.json` entry cleared (or corrected via the Gaming Journal's title field) to re-resolve correctly.
- **A modpack's variant training-data bootstrap produced a near-duplicate of the base game's doc instead of pack-specific notes** (2026-07-13) — its web search query (`game_knowledge_bootstrap.py`'s `bootstrap_variant_knowledge`) mixed the base game's name into a long phrase (`"{modpack} {base_title} modpack overview features progression guide"`); official/high-authority base-game domains (minecraft.net, the wiki) dominate almost any query containing the base game's name, so SearXNG returned the same generic base-game material the base bootstrap already got, and the LLM had nothing pack-specific to work from. Fixed by shortening the query to just `"{modpack} modpack"` (same "plain keyword queries" discipline as `system_companion.md`'s Web Search section). Reminder: this doc type is scoped to "how to read this game's screen" only, never general mechanics/lore (see `game_knowledge_bootstrap.md`) — some genuine overlap with the base game's doc (unchanged vanilla HUD elements) is still expected and correct, not a bug.

- YouTube in-app player (`youtube-player.js`): uses `playerVars.controls:0` + a custom volume slider — YouTube's native volume popout renders outside our small docked panel and loses the mouse. `play_on_youtube` auto-queues YouTube's generated "Mix" (`RD<video_id>` via yt-dlp) so next/previous have something to walk — that's an algorithmic mix, not the user's real playlist (use `play_youtube_playlist` for that). The panel is always docked above the chat log now (2026-07-05, floating/draggable mode was removed) — the only way to detach it is popping out to a real window (native pywebview window or Document PiP).
